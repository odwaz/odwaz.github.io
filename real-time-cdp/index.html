Gimba — Real-time CDP

A multi-tenant customer data platform on reactive Java. Any application posts events over a published HTTP contract; Gimba runs them through a four-stage Kafka pipeline that stitches identities into one profile per customer, computes traits, re-evaluates segments, and tells the application who entered or left a segment in an ES256-signed, encrypted webhook. Nothing in the request path waits on the pipeline.

Java 17 · Spring Boot 4 Spring WebFlux · R2DBC Apache Kafka (KRaft) PostgreSQL JSONB Solo project: design to deploy

High-level design

One Spring Boot application split into Spring Modulith modules. The ingestion API stores and acknowledges; four Kafka stages do the rest, each keyed by profile so one customer's events stay in order.

Ingestion, pipeline and delivery

Dashed boxes are other organisations' systems. Solid lines are HTTP; dotted lines are Kafka topics, each with 6 partitions and keyed by profile. Every stage has a dead-letter path.

Low-level design

1. Event to profile to segment

The event is stored before it is published. If the publish fails the client is told to retry with the same eventId; that retry publishes the stored event instead of storing a second copy, and a retry of an event already published is acknowledged as duplicate_ignored.

2. Webhook delivery

The app verifies the token with Gimba's public key, shared out of band, decrypts the body with its own key, checks the token's hash against it, and de-duplicates on X-Delivery-Id, which is stable across retries. Its reply is stored as the outcome, so analytics can show what each segment change led to.

3. Failure and compensation

WhenWhat happens
Client retries an eventSame eventId: acknowledged duplicate_ignored, or published now if the first publish never happened. Header and body ids that differ are rejected.
Wrong key, bad schema, no identity401 / 400 before anything is stored. A key used against another tenant's data is a 403 tenant conflict.
Kafka redelivers to the profile engineThe profile keeps the ids of the events it has applied (the last 100), so a redelivered or out-of-order event is applied exactly once.
A stage keeps failing on a recordThe error handler retries, then publishes it to a dead-letter topic; the monitor logs an ERROR and counts it on gimba.dead_letters.
App unreachable or overloaded5xx, 408 and 429 are retried, up to four attempts; every attempt and response is in webhook_logs.
App rejects the webhook (other 4xx)Treated as permanent: retrying the same request can't fix it.
Webhook pointed at an internal addressRefused by the target policy unless the host is explicitly allow-listed.
A profile needs rebuildingProfiles are a projection of the append-only event log and can be replayed from it.

The tenant comes from the app whose key signed the token, never from the body. The token holds only who sent it, to whom, until when, and a hash of the message's contract fields, so it shows nothing about the event. The webhook carries the profile's traits, so the app can act without calling back.

Security

  • Apps sign every request with their own P-256 key (ES256) and encrypt the body to Gimba's; Gimba stores only their public keys. The signing app decides the tenant, so a payload can't write into another tenant.
  • Admin users log in with a JWT; their roles are per tenant and re-read on each request (cached 30 s), so removing a role takes effect without waiting for the token to expire.
  • Admin routes are matched on the decoded path, so encoded or dotted paths can't skip a rule.
  • Segment rules compile to parameterised SQL from a parsed AST: no expression evaluation and no string-built queries.
  • Webhooks and responses are signed with Gimba's own ES256 key and encrypted to the app's; webhooks to internal targets are refused unless allow-listed.
