SpazaAPi

Online ordering and delivery for South African spaza shops: a storefront, a merchant dashboard and a driver app on top of an API gateway and six Spring Boot services. Checkout is synchronous where money moves and event-driven everywhere else: stock and deliveries follow order events on Kafka, and orders follow delivery events back. Deployed to Amazon EKS in Cape Town.

Spring Boot 2.7 · Java 17 services Spring Cloud Gateway · Boot 3.4 · Java 21 Apache Kafka PostgreSQL Solo project: services, UI, infra and pipeline

High-level design

Every request enters through the gateway. Services own their tables and talk over Kafka for anything that can happen after the response; the few calls that must happen inside a request are plain HTTP between services.

Services, ports and what connects them

Dashed boxes belong to other organisations. Solid lines are synchronous HTTP; dotted lines are Kafka. Four services (catalog, order, payment, delivery) report customer activity to the CDP; its signed segment callbacks land on customer-service.

Low-level design

1. Checkout

Money is settled inside the request; stock and delivery follow from the event.

The wallet is debited after the order commits. The wallet lives in another service and cannot roll back with order's transaction: debiting first could charge a customer for an order that then fails to save, and payment-service exposes no credit endpoint to compensate with. Order also sends order_placed to the CDP at step 6; that call never blocks checkout.

2. Delivery lifecycle

The driver moves the job; the order follows by two independent paths.

Delivery status maps onto order status as: assigned or picked up → PROCESSING, in transit → SHIPPED, delivered → DELIVERED, and failed, cancelled, unreachable or returned → CANCELLED. The two paths (4a, 4b) can arrive in either order or twice; the backwards-status rule in step 6 makes that harmless.

3. Failure and compensation

WhenWhat happens
Wallet debit fails after commitThe order stays, its paymentStatus is written as FAILED in its own transaction and an ERROR is logged, so the unpaid order is visible to the merchant and queryable for reconciliation.
Order cancelledOrder publishes ORDER_CANCELLED. Catalog adds the items back to stock and marks them available; delivery cancels the job if the driver hasn't picked it up yet.
Delivery fails at the doorFailed, cancelled, customer unreachable and returned all map to order CANCELLED; the driver is freed and, for an unreachable customer, the customer is notified by SMS.
order-service down when a delivery movesThe HTTP update is retried three times with backoff, then stored in failed_events and retried every 2 minutes for 24 hours. The Kafka path delivers independently.
Delivery events out of order or repeatedOrder ignores any status that ranks below the current one, so a late DELIVERY_IN_TRANSIT cannot undo DELIVERED.
ORDER_PLACED delivered twiceDelivery creates a job only if none exists for the order id.
Payment webhook retriedThe webhook is verified first (signature), then de-duplicated on the provider's event or transaction id, stored in a per-provider log with a unique key; a repeat returns 200 and changes nothing.
Driver goes quietA job assigned but not picked up for 30 minutes returns to the pool; a driver with no location update for 5 minutes is marked offline.
CDP unreachableEvents are retried with backoff (server errors only, never 4xx) and then logged and dropped; checkout and delivery never wait on the CDP.

Security at the edge

  • The gateway verifies every token's signature, strips any identity headers the client sent, and sets its own from the verified claims. Services read identity only from those headers.
  • /private/** and business analytics are staff-only. A driver can act only on deliveries and profile routes carrying their own driver id.
  • Staff tokens carry the staff member's merchantId; merchant payment configuration and store changes are allowed only for the caller's own merchant, or a platform admin.
  • Service-to-service endpoints (/api/v1/internal/**, order status from delivery) require a shared service token and are not routed by the gateway.
  • Payment-provider webhooks are rejected unless their signature verifies and the amount matches what was charged.

Known limits

  • Stock is decremented when ORDER_PLACED is consumed, not reserved at checkout, and the stock consumer does not yet de-duplicate by event id, so a redelivered event can decrement twice.
  • A provider-confirmed card or EFT payment updates payment-service's transaction; order-service is not yet told, so those orders' paymentStatus is not moved to PAID.
  • CDP events are retried but not stored in an outbox, so an event whose retries run out is lost to the CDP.
  • Rate limits and OTP codes live in one pod's memory; more replicas would need a shared store.
