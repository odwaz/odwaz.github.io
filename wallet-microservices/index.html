Wallet Microservices

A rand wallet built as an API gateway and four reactive Spring Boot services on WebFlux and R2DBC. Every money movement is a balanced journal in a double-entry ledger, is safe to retry with an idempotency key, and leaves through a transactional outbox written in the same database transaction. Ships through GitOps onto Terraform-provisioned AWS.

Java 17 Spring Boot 3.4 · WebFlux R2DBC · PostgreSQL ArgoCD GitOps Solo project: services, UI, infra and pipeline

High-level design

Money moves synchronously inside wallet-service's own transaction. Everything that reports on it happens afterwards, from an outbox, so a slow or failing downstream can never block or lose a payment.

Services, ports and what connects them

Dashed boxes belong to other organisations. Solid lines are synchronous HTTP; dotted lines are asynchronous delivery. There is no message broker: the outbox table is the queue, drained over HTTP with retries, and a shared-dtos module keeps the contracts between services from drifting.

Low-level design

1. Transfer

One reactive transaction moves the money and records the event; delivery happens afterwards.

Top-ups and withdrawals take the same shape with a system account on the other side of the journal (SETTLEMENT_EXTERNAL), so the ledger always balances. GET /wallets/{id}/reconcile compares the cached balance with the balance derived from the ledger.

2. Sign-in and CDP callbacks

A callback with no delivery id, a bad signature or a malformed body is rejected before anything is stored. The CDP's public key is shared out of band, so only the CDP can produce a valid signature.

3. Failure and compensation

WhenWhat happens
Client retries a transferSame Idempotency-Key and body returns the stored response; nothing moves twice. Same key with a different body is a 409. A retry while the first is still running is told it's in progress rather than raced.
Insufficient funds or someone else's walletRejected before the transaction opens; nothing is written.
Journal doesn't balance, a save fails, or a concurrent update winsThe whole R2DBC transaction rolls back: journal, both balances and the outbox row together. A stale @Version means no lost update.
transaction-service downThe outbox row waits with exponential backoff up to 15 minutes; after 10 attempts (about 35 minutes) it is parked FAILED, counted in a periodic report, and replayable through /internal/outbox/{id}/replay.
Publisher dies mid-sendA claim older than 2 minutes is reclaimed and the row re-sent; transaction-service's unique transactionId turns the repeat into a no-op.
CDP down or rate-limitingThe transaction stays cdp_state = PENDING; 5xx, 408 and 429 are retried (429 after its Retry-After) and a sweep re-sends pending rows every 60 s.
CDP rejects the event (other 4xx)Marked REJECTED and logged as a contract violation: retrying a bad request can't fix it.
Forged or replayed callbackForged: signature fails, 401. Replayed: the delivery id is already claimed, so nothing changes.
Cached balance drifts from the ledgerGET /wallets/{id}/reconcile reports both; balances are only ever written alongside a journal.

Security at the edge

  • The gateway verifies the JWT, removes any X-User-* header the client sent and sets its own from the verified claims. Routes are matched on the decoded path, so an encoded or dotted path can't slip past a rule.
  • Sign-in needs the password and then a one-time code (5 minutes, 5 attempts) before a token is issued.
  • Money endpoints only act on the caller's own wallet: a transfer's source must belong to the caller, and idempotency keys are scoped to the caller so one user's key can't replay another's response.
  • CDP callbacks carry no user token; they're accepted only with a valid Ed25519 signature over the raw body.
