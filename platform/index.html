Platform Infrastructure

One Terraform repo that provisions the entire AWS platform — EKS on Fargate, RDS PostgreSQL Multi-AZ, Strimzi Kafka, per-service CI/CD, and a Prometheus/Grafana observability stack — deliberately kept separate from the application code. Eight reusable modules, composed per environment, with remote state in S3 and DynamoDB locking.

Terraform AWS EKS / Fargate Strimzi Kafka Prometheus + Grafana af-south-1 · dev / prod

Platform architecture — Route 53 → ALB → EKS/Fargate, backed by RDS & Kafka

infra repo ✓ provisioned by Terraform — the application code lives in its own repos and rolls out on top

What it provisions

Eight reusable modules under modules/, composed per environment in environments/dev and environments/prod.

networking

VPC across two AZs — public/private subnets, route tables, and NAT gateways (single NAT in dev to save cost, per-AZ in prod).

eks

EKS cluster on Fargate profiles (k8s 1.29) — no node groups to patch. Namespaces for the services, Kafka, and monitoring.

rds

PostgreSQL in private subnets — single-AZ db.t3.micro in dev, Multi-AZ db.r6g.large in prod.

kafka

Strimzi operator installed via Helm; a KRaft-mode Kafka cluster (single broker in dev, three in prod) for the event-driven services.

ecr

Three container registries — one per service — that the pipelines push images to and EKS pulls from.

monitoring

kube-prometheus-stack via Helm — Prometheus scraping workloads and Grafana dashboards, with an admin password injected as a variable.

pipeline

Per-service CodePipeline + CodeBuild, wired to GitHub through a CodeStar connection — source, build, push to ECR, deploy to EKS.

dns

Route 53 records and ACM certificates fronting the ALB, so services are reachable over HTTPS on real hostnames.

Infrastructure as code & state

Environments are thin compositions of the modules; state is remote, encrypted, and locked so applies are safe to run from anywhere.

backend.tf — remote state on S3 with DynamoDB locking (bootstrapped per environment)

# Remote state configuration — S3 + DynamoDB locking.
terraform {
  backend "s3" {
    bucket         = "gimba-terraform-state"
    key            = "environments/dev/terraform.tfstate"
    region         = "af-south-1"
    dynamodb_table = "gimba-terraform-locks"
    encrypt        = true
  }
}

environments/dev/main.tf — modules composed for one environment (excerpt)

module "eks" {
  source          = "../../modules/eks"
  project         = var.project
  environment     = var.environment
  cluster_version = "1.29"       # Fargate: default, kafka, monitoring namespaces

module "pipeline" {
  source                  = "../../modules/pipeline"

  branch                  = each.value.branch
  codestar_connection_arn = var.codestar_connection_arn
}

Engineering highlights

The point of the repo is a platform you can stand up, reason about, and tear down — reproducibly.

Infrastructure separated from application code

All AWS provisioning lives in this one repo, not inside the services. Infra changes and app deploys move on their own cadence, with their own review and their own credentials — the app pipelines never hold cluster-admin rights.

Remote, locked Terraform state

State is stored in an S3 bucket with encrypt = true and a DynamoDB lock table, keyed by environment path — safe concurrent applies and no state on a laptop.

Serverless Kubernetes with Fargate

EKS runs on Fargate profiles, so there are no worker nodes to patch or scale — the cluster schedules pods onto managed capacity across the service, Kafka, and monitoring namespaces.

Kafka and monitoring as Helm-managed platform services

Strimzi (KRaft-mode Kafka) and the kube-prometheus-stack are installed through the Helm provider from Terraform — the messaging backbone and the observability stack are part of the same reproducible apply.

Cost-aware environments

Dev trades away HA for cost — a single NAT gateway, single-AZ db.t3.micro, one Kafka broker — while prod turns on Multi-AZ RDS, db.r6g.large, and three brokers. Same modules, different variables.

Environments

dev — cost-optimized

  • NAT gateway: single
  • RDS: db.t3.micro · single-AZ
  • Kafka: 1 broker · no persistence
  • Compute: EKS Fargate

prod — highly available

  • NAT gateway: per-AZ
  • RDS: db.r6g.large · Multi-AZ
  • Kafka: 3 brokers · persistent
  • Compute: EKS Fargate
