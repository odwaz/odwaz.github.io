Cloud Deployments

Three services, deployed three genuinely different ways — GitOps to Kubernetes, raw manifests to Kubernetes, and a container on a plain VM. The only things they share are that every one is provisioned with Terraform and runs on AWS. Beyond that, each has its own CI system, its own delivery model, and its own compute target.

Deployed three ways

Same discipline — infrastructure as code, a quality gate, a repeatable pipeline — expressed through three different delivery models and two different compute services.

wallet-microservices

EKS · GitOps

GitLab CI/CD builds the service images to ECR and updates the Git desired-state. ArgoCD watches that repo and syncs it onto Amazon EKS — pull-based GitOps, so the pipeline never holds cluster-admin credentials.

real-time-cdp (Gimba)

EKS · manifests

GitLab CI runs the build and the SonarCloud gate, then applies Kubernetes manifests directly with kubectl. The event-driven CDP runs on Amazon EKS alongside its Apache Kafka.

sme-directory

EC2 · Docker

GitHub Actions builds the Spring Boot jar, gates it with SonarCloud, and packages it as a Docker image in ECR — then runs that container on an Amazon EC2 instance backed by RDS. Containerized, but without a Kubernetes control plane.

The common thread — IaC on AWS

Whatever the runtime, the AWS footprint under each service is defined in Terraform, with state kept remote, encrypted, and locked so an apply is safe to run from anywhere.

backend.tf — remote state on S3 with DynamoDB locking

# Remote state — S3 backend, DynamoDB locking, per-environment key.
terraform {
  backend "s3" {
    bucket         = "gimba-terraform-state"
    key            = "environments/dev/terraform.tfstate"
    region         = "af-south-1"
    dynamodb_table = "gimba-terraform-locks"
    encrypt        = true
  }
}

One toolchain philosophy, three targets

Each service still gets the same treatment — a version-controlled pipeline, a SonarCloud quality gate, and Terraform-defined infrastructure — but the delivery model is matched to the workload: GitOps where the cluster should self-heal, plain manifests where a direct apply is simplest, and a container on a VM where a full Kubernetes control plane would be overkill.

Least-privilege delivery

The GitOps path (ArgoCD) means the wallet pipeline never holds cluster credentials — it writes desired state to Git and the cluster pulls. The EC2 path pulls a container image from ECR onto the host. Different trust models, each scoped to what that deployment actually needs.
