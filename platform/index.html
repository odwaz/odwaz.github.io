Cloud Deployments

Each project deploys to AWS from code: Terraform defines the infrastructure and a pipeline builds and ships the services. What differs is the delivery path: Argo CD GitOps or a kubectl deploy from the pipeline.

Three delivery paths

How each project gets from a commit to a cluster.

wallet-microservices

EKS · GitOps

Terraform defines the VPC, the EKS cluster, RDS and ECR, and installs Argo CD with Helm. GitLab CI/CD builds and tests the services, scans them with Trivy and pushes the images to ECR. Argo CD syncs the Kustomize overlays for dev and staging onto the cluster, so the pipeline never needs cluster credentials.

SpazaAPi

EKS · kubectl

Terraform defines the VPC, the EKS cluster, RDS PostgreSQL, ECR and an EC2 instance for the web front end, in AWS's Cape Town region. GitLab CI/CD builds, tests and runs the SonarCloud gate, pushes the images, then deploys with kubectl: it applies the manifests, sets the new images and waits for every rollout to finish.

Orchestrator releases

Kubernetes · GitOps

When a change merges, the agent orchestrator opens a release pull request in a separate deployments repository that lists what should be running. Argo CD keeps a cluster in line with that repository, so merging a release deploys it and reverting the commit rolls it back. It releases a test application to three clusters: a local kind cluster, k3s on an AWS instance, and staging on EKS with blue/green releases through Argo Rollouts. After each sync Argo CD runs a smoke check; a fresh release that fails it gets a rollback pull request, merged automatically on dev.

Gimba and SME Directory

Both have pipelines, but no deployment is defined in their repositories yet. Gimba's GitLab CI builds, tests, runs the SonarCloud gate and packages the jar. SME Directory runs SonarCloud on GitHub Actions. Gimba also has Kubernetes manifests for itself and Kafka, ready for a cluster.

The common thread — infrastructure as code

The AWS side of the wallet and SpazaAPi is defined in Terraform, with state kept in Terraform Cloud: one workspace per stack, stored remotely and locked while a run is in progress.

versions.tf — remote state in Terraform Cloud, one workspace per stack

# Each stack has its own Terraform Cloud workspace, so its state is separate from every other stack.
terraform {
  cloud {
    organization = "devwork"
    workspaces {
      name = "wallet-dev"
    }
  }
}

Why two delivery styles

GitOps where the cluster's state should come from Git and every change is a reviewable commit: the wallet and the orchestrator's releases. A direct kubectl deploy where one pipeline owning the rollout is simpler: SpazaAPi.

Who holds which credentials

With Argo CD, the wallet's pipeline has no cluster credentials: it pushes images and the cluster pulls its desired state from Git. SpazaAPi's pipeline deploys directly, so it does need cluster access.
